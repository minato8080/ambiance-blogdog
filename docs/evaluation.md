# 類似記事検索の評価手順

Embedding の次元削減・半精度化（halfvec）や文体特徴量の追加によって、検索結果と容量がどう変わるかを既存データで確かめるための手順。ツールは `cmd/evalsearch`（開発用。本番にはデプロイしない）。

## 前提

- 本番 DB へは**読み取り専用トランザクション**（`BEGIN READ ONLY`）でのみ接続する。書き込みは行わない。
- 接続先は `-db` か環境変数 `DATABASE_URL` で指定する。
- 取り出したデータは `eval-data/`（`.gitignore` 済み）に保存する。記事 URL・本文抜粋を含むためコミットしないこと。
- `export` は全記事の Embedding を転送する（`vector(1536)` なら2万件規模で約150MB、`halfvec(512)` 移行後は約50MB）。Neon のデータ転送量に注意。
- `export` / `dbcheck` は `articles.embedding` の型（`vector` / `halfvec`）を見て動くので、`006_articles_embedding_halfvec` の適用前後どちらでも使える。ただし適用後のデータセットは 512 次元なので、`dims` で 1536 / 1024 は指定できない。

## 1. 現状の計測（`dbcheck`）

```bash
go run ./cmd/evalsearch dbcheck -queries 30
```

表示内容:

- PostgreSQL / pgvector のバージョン、DB 全体の容量
- テーブル別（本体・TOAST・索引）、索引別の容量
- `articles` の列別の平均バイト数と合計（`embedding` / `summary` / `title`）
- 1ブログあたりの最大記事数と、5件を超えるブログの数
- 本番と同じ検索 SQL で「索引あり（現行設定）」と「全件比較」を実行した結果
  - 索引ありの recall（全件比較を正解とした一致率）と、件数が `k` 未満だったクエリ数
  - クライアント側で計ったレイテンシ（p50 / p95 / 最大。ネットワーク往復を含む）
  - 1件目のクエリの `EXPLAIN (ANALYZE, BUFFERS)`

## 2. データの取り出し（`export`）

```bash
go run ./cmd/evalsearch export -out eval-data/articles.bin
```

`embedding` を持つ全記事の `id, blog_id, url, title, summary, embedding` を保存する。以降のコマンドはこのファイルだけを使い、DB には接続しない。

## 3. 次元削減の影響（`dims`）

```bash
go run ./cmd/evalsearch dims -dims 1536,1024,512,256 -queries 500
```

- 基準: 現行と同じ `vector(1536)`（float32）での全件比較。同一ブログは除外する（本番と同じ条件）。
- 比較対象: 先頭 N 次元に切り詰め → L2 正規化 → 半精度に丸めたもの。`l2_normalize(subvector(embedding, 1, N))::halfvec(N)` に相当する。
- 指標:
  - `recall@k`: 基準の上位 k 件のうち、同じ記事が入った割合
  - `1位一致率`: 1位が基準と同じだった割合
  - `類似度保持率`: 結果の「1536次元での類似度」の合計 ÷ 基準結果の合計。1 に近いほど、別の記事が入れ替わっていても同じくらい近い記事を返している
- 目安: `halfvec(1536)` がほぼ 1.0 になる（半精度化の影響が小さい）ことを確認したうえで、512 / 256 を判断する。採用ラインの例は `recall@10 ≥ 0.9` かつ `類似度保持率 ≥ 0.98`。

## 4. 文体特徴量の効果（`style`）

```bash
go run ./cmd/evalsearch style -dim 512 -pool 100 -alphas 1,0.9,0.8,0.7,0.5 -queries 1000
```

- 文体特徴量: `internal/style` が `summary`（本文の先頭500文字、タイトルは含まない）から 23 次元を計算する。内容は文字種の比率、句読点・感嘆符・括弧・絵文字の頻度、文の長さとばらつき、です・ます調／だ・である調の割合、文末の「ね・よ・な」、一人称（私・僕・俺）、文末の「笑・w・草」など。コーパス全体で z-score 化して比較する。
- 並べ替え: Embedding で上位 `pool` 件を取り出し、`alpha × Embedding類似度 + (1 − alpha) × 文体類似度` で並べ替える。
- 表 [A] 著者当て（自分自身だけ除外）: 同じ著者の記事は文体が似るため、文体を捉えているほど同じブログの記事が上位に来る。
  - `同ブログHit@k` / `同ブログMRR@k`
  - `主題が遠い同ブログHit@k`: 同じブログの記事のうち、1536次元の類似度が同ブログ記事ペアの中央値より低いもの（主題が違うもの）が上位に入った割合。主題の近さで当たっている分を除いて見るための指標。
- 表 [B] 本番条件（同一ブログ除外）: `主題の近さ`（1536次元類似度の平均）、`文体の近さ`、`現行結果との重複率`。alpha を下げたときに主題がどれだけ離れるかを見る。
- 行「参考: 文体のみ（全件）」は文体特徴量だけで全件から探した場合で、文体特徴量そのものの識別力の目安。

注意:

- 著者当ては文体の代わりとして使う指標で、「読んで雰囲気が似ている」とは一致しない。最終判断は 5 の目視評価で行う。
- `summary` は500文字の抜粋なので、全文から計算した場合より特徴量のブレが大きい。

## 5. 目視評価（`blind` / `blind-score`）

```bash
go run ./cmd/evalsearch blind -a "dim=1536,half=false,alpha=1" -b "dim=512,half=true,alpha=0.8,pool=100" -queries 30 -k 5
```

1. `eval-data/blind/blind_sheet.csv` を Excel 等で開く。各クエリについて、A・B 両方の上位 k 件をまとめてシャッフルした候補が並ぶ（どちらの方式の結果かは書かれていない）。
2. 各候補の `style_score`（文体・雰囲気の近さ）と `topic_score`（主題の近さ）を 0〜2 で入力する。採点しない行は両方とも空欄にする。
3. 採点後に集計する（`blind_key.csv` は採点が終わるまで開かない）。

```bash
go run ./cmd/evalsearch blind-score -dir eval-data/blind
```

方式ごとに採点済み件数と平均点を表示する。両方の方式に入った候補は両方に数える。

## 方式の指定方法

`-a` / `-b` は `キー=値` をカンマで区切って指定する。

| キー | 既定値 | 説明 |
| ---- | ------ | ---- |
| `dim` | 1536 | Embedding の次元数 |
| `half` | false | 半精度（halfvec）に丸めるか |
| `alpha` | 1 | Embedding 類似度の重み（1 なら Embedding のみ） |
| `pool` | 100 | Embedding で取り出す候補数（0 なら全件を並べ替え対象にする） |

## 共通フラグ

| フラグ | 既定値 | 説明 |
| ------ | ------ | ---- |
| `-in` | `eval-data/articles.bin` | データセット |
| `-k` | 10（`blind` は 5） | 上位何件を比較するか |
| `-queries` | コマンドごと | クエリ数（`dims` / `style` は 0 で全件） |
| `-seed` | 42 | クエリ抽出の乱数シード（同じ値なら同じクエリになる） |
